# VECTOR repair analysis — October 27, 2026

## What the documentation says the game should do

The Markdown docs describe VECTOR 1.3 as a 12-mode reflex game with local guest progression and optional Google accounts. Guest progress belongs to the browser. Signed-in accounts should have a separate cloud-backed wallet, inventory, gifts, name changes, missions, daily rewards, and a global scoreboard. Developer tools should publish Store items and player changes into the live game. Gifts should transfer a cosmetic out of the sender's vault and deliver it to the recipient. Completed scored runs should publish personal bests to the correct mode/day/week challenge bucket and update the scoreboard live.

`docs/FIREBASE-SETUP.md` describes the authoritative design: trusted Cloud Functions, transactions/receipts, a verified owner email, an expiring master-key session, and coordinated deployment of Functions, Firestore rules, Storage rules, and the client. `UPGRADE-1.3.md` and `PROJECT-STATUS.md` also say the CLI was unauthenticated and no production backend changes were made, so their deployment claims are not evidence of a live deployment.

## Root causes found

1. **Production never called its trusted backend.** `callAccount()` only invoked Cloud Functions when `VITE_VECTOR_EMULATORS=true`. In production it always used a partial client fallback.
2. **The fallback was incomplete and silently optimistic.** It did not persist gift documents, recipient/sender account changes, run sessions, receipts, or leaderboard records. Most Firestore failures were caught and converted into UI success messages.
3. **Player search blocked gifting.** `playerDirectory` required Developer or Moderator access, so a normal signed-in player could not find a recipient.
4. **Gift rules blocked status changes.** A recipient could not accept or return a gift because writes were allowed only when `request.auth.uid` equalled the gift's sender.
5. **Signed-in runs skipped live score publication.** `App.tsx` called `submitScore()` only in the guest branch. The signed-in branch relied on `recordRun`, whose fallback never wrote a leaderboard document. Daily/weekly scores also needed the run's own challenge bucket rather than the current clock.
6. **Developer changes were not durable.** Catalog writes were best-effort, off-line edits lived in an account-scoped save slot, and admin writes did not use atomic account/player/audit writes. Image uploads sent a data URL to a Function that expected raw base64.
7. **The requested master key could not be entered.** The form required 16–256 characters, the Function required 16–256 characters, and the client fallback accepted an unrelated email string instead of the requested key.
8. **Sign-out could leak a stale snapshot.** React state from a level-21 account could be written into the fresh guest save scope during the identity transition, and sign-out did not first flush the canonical account snapshot.

## Repairs implemented

- `callAccount()` now tries the deployed trusted Functions first, with a short cached outage window, then falls back to a complete Firestore/domain engine on missing/unavailable Functions. Server-side permission and validation errors are still shown rather than masked.
- New `src/firebase/accountFallback.ts` implements transactional bootstrap, game actions, receipts, run sessions, gifts, admin actions, player directory, catalog publishing, image/profile changes, feedback, inspection, and leaderboard publication. It writes account and public-player records together and records admin activity.
- Gifting now writes gift documents, uses a public player directory available to any signed-in player, validates recipient accounts, supports accept/cancel, and defers a recipient-initiated return credit to the sender's next sync so the recipient never writes another player's private account document.
- `firestore.rules` now allows targeted gift lookups and participant status updates while keeping ownership fields immutable. It also protects role escalation, leaderboard ownership, run ownership, and legacy balance writes.
- Developer catalog edits are cached globally (not per account), published with an audit record, queued in a durable outbox on failure, and immediately injected into the live `STORE_ITEMS`, frames, banners, and titles. Cloud Function image validation accepts optimized data URIs, and the client sends both raw base64 and the data URL.
- The owner-requested Developer key is configured. The browser bundle contains no plaintext key; `functions/src/master-key.mjs` stores a salted PBKDF2-SHA256 verification record. The UI and Function accept an 8-character minimum, grant one hour of access, and still allow a longer private hash override. Because an eight-digit key is weak, it should be treated as a convenience gate and rotated if exposed.
- Completed runs now save a device score in the exact challenge bucket, publish to the global leaderboard for both guest and signed-in paths, and queue authenticated failed publications for retry on sign-in or reconnect. The fallback run settlement also writes mode and overall leaderboard records transactionally.
- Sign-out flushes the canonical account state, preferences, and pending scores before Firebase signs out. `App.tsx` now tracks the save scope from which its state was loaded, so stale account values cannot be written into the guest slot. The level-21 account remains in its own cloud/device slot and returns on the next sign-in; guest-only progress is shown immediately after sign-out.
- `syncUserProfileToCloud()` now writes only the public `players` record, keeping private progression in the account service instead of an incompatible legacy `users` shape.

## Deployment note

This workspace can change source, rules, and tests, but it cannot deploy the live Firebase project on the owner's behalf. For authoritative production behavior, deploy the Functions, updated Firestore/Storage rules, and new `dist/` together using `docs/FIREBASE-SETUP.md`. Until that deployment is complete, the upgraded client fallback keeps developer edits, gifts, scores, and account progress working on the device and through the existing Firestore project where rules permit.
